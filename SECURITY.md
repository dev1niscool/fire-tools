# Security and local state

Use the supplied Windows, macOS or Linux launcher in the extracted source with an installed Python interpreter you trust. Use Windows or Linux for operations that change a tablet or save an undo record. These launchers use Python isolated mode and omit site startup hooks. Direct Python invocations follow your interpreter’s normal startup configuration. Supply official Google Platform-Tools and Build Tools and a trusted Java runtime. The toolkit executes those selected paths locally. A malicious replacement executable or JAR could run with your computer account's permissions.

The toolkit has no telemetry, auto-updater or automatic downloads. Its network-related actions consist of ADB requests to the local ADB server, explicit connections to user-selected wireless-debugging endpoints, and opening fixed documentation and vendor links on request. Legacy wireless ADB is not encrypted Android pairing; use a trusted private network and return to USB when finished. Your external tools, browser and installed Google apps may make their own network requests.

Changes require an explicit tablet serial and confirmation. The service checks the selected tablet's manufacturer, model, Android API level and active Android user before making a change. The desktop checks that the reviewed device still matches the tablet selected under Connection. For Wi-Fi changes, Fire Tools also requires a hardware serial reported by the tablet. Before applying the reviewed plan it binds commands to one live ADB transport ID and rechecks the device. A disconnect or reassigned address stops that operation. These checks assume trustworthy tablet properties and a trusted, continuously running local ADB server. ADB debugging authorization applies to your computer. Revoke that authorization from the tablet when you are finished if it is no longer needed.

Fire Tools ships no Windows USB driver. If ADB already sees your tablet, including an `unauthorized` entry, a separate download is usually unnecessary. [USB driver setup and signature findings](https://dev1niscool.github.io/fire-tools/drivers.html)

The offline Google signature check uses the API level you enter. Compare the reported APK architectures with the ABIs in Connection before installing. A whole-file scan-record match identifies the specific bytes previously examined. [APKMirror audit](https://dev1niscool.github.io/fire-tools/apkmirror.html)

Google Play installation verifies all selected APKs with Google's `apksigner.jar` for the tablet’s Android API. Fire Tools requires the pinned Google first-party Android production certificate. For the specific Play services key rotation observed in v46 it accepts the known successor only after checking its v3 signature and the two-certificate signing lineage rooted in that pin. The package allowlist, archive and compatibility checks and staged-file rechecks constrain what the installer accepts. The Play installer reads back each installed APK and compares its SHA-256 with the reviewed input. Adding sync to an existing installation verifies the installed core Google packages, and sync-provider enablement requires an Android system package. A valid signature identifies the signer. It cannot establish that an APK is suitable for your tablet or that its code is safe to run. [AndroidX certificate reference](https://android.googlesource.com/platform/frameworks/support/+/7be3a623dfcf461ff6e2004799ac2e652c8d23a8)

Generic sideloading verifies APK signatures and shows the signer identity. You can supply an expected fingerprint to restrict which publisher is accepted. Core Google Play packages require Google's trusted signing identity. The standard F-Droid client (`org.fdroid.fdroid`) requires F-Droid’s published Android certificate even in the general APK installers. **Tools → Install F-Droid** also rejects any other package ID. [F-Droid signing keys](https://f-droid.org/docs/Release_Channels_and_Signing_Keys/)

The source-built ad helper uses a locally generated signing identity. Its dedicated grant workflow checks the installed helper against the fingerprint you supply. Obtain that fingerprint from your own trusted build.

Advanced commands can delete app data, remove secondary profiles, alter permission grants, block security updates, change connectivity or run user-specified device shell commands. Those actions require a review and confirmation and may not be reversible. Core package guards constrain the guided app tools; the expert shell is intentionally a general device command interface. It uses ordinary ADB shell privileges, never a host shell or an elevated exploit mode.

Backups, APK exports, screenshots and logs stay at paths you choose and can contain personal data. Configuration backups cover supported settings and package state, not firmware or all private app data. File operations are limited to shared storage in the guided tools. Published source archives contain no backups, device logs, keys, APKs or SDK executables.

The optional ad helper declares no network permission, disables Android backup, and stores its state privately on the tablet. Its notification must remain enabled while monitoring. Restore the saved setting before clearing its data or uninstalling it. See [helper source and build instructions](companion/README.md).

## Undo state and operation lock

| Platform | State directory |
| --- | --- |
| Windows | `%LOCALAPPDATA%\open-fire-toolkit` with the user's home directory as fallback |
| Linux | `$XDG_STATE_HOME/open-fire-toolkit` or `~/.local/state/open-fire-toolkit` |

`state.json` stores the saved lock-screen setting and, for paired suppression, the exact Special Offers package mode, associated with a serial hash and the reported model. Wi-Fi uses a hash of the tablet’s boot serial, with its reported hardware serial as fallback. USB can use its serial selector if these properties are unavailable. A matching hardware serial lets the same tablet use its saved records across USB and Wi-Fi. Older records tied only to a Wi-Fi address cannot establish tablet identity and are ineligible for automatic restore. Their files are preserved. Preserve this file while a restore may still be needed. The toolkit does not collect account passwords or Google credentials.

`packages-state.json` stores package recovery targets, `device-settings-<serial hash>.json` stores settings undo, and `private-dns-<serial hash>.json` stores the prior resolver configuration. Keep the complete state directory until you finish restoring changes. These files are not part of the source release. State and output directories are pinned during writes; symlinked or reparse-point paths are refused.

`operation.lock` prevents concurrent writes by toolkit processes sharing that directory. If a forced exit leaves it behind, close every instance of the toolkit and confirm any in-flight device operation has finished before removing only `operation.lock`. Reconnect and review the tablet's current state before retrying. Preserve `state.json` if it becomes unreadable.

## Experimental browser tools

In desktop Chrome, the published page asks you to select a USB device and approve debugging on the tablet. It generates a new ADB key for each connection. Leave “Always allow” unchecked. Changes require the primary adult profile, confirmation, an exclusive browser lock and a fresh device identity check. USB grants and browser storage belong to the website origin. Recovery records for guided changes stay in this browser profile. Clearing site data can erase them.

If you save the four-file Google set in Chrome, its APK bytes stay in local IndexedDB. Loading the set checks all four hashes again. Forgetting it or clearing site data removes the saved set. The Google installer accepts files that exactly match six previously audited APKs. It compares local SHA-256 digests, checks the connected tablet’s SDK and processor, and verifies installed bytes over USB. The page uses bundled local code and a content security policy that blocks network requests from its scripts. Sign-in happens on the tablet. The Android shell, package manager and Fire OS determine which operations succeed.
